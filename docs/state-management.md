# Управление состоянием во фронтенде WMS

---

## 1. Общая концепция

В приложении используется гибридный подход:

- **Глобальное состояние** — NgRx SignalStore (для данных, общих для
  многих компонентов: пользователь, уведомления).
- **Локальное состояние** — простые сигналы (`signal()`, `computed()`)
  внутри компонентов.
- **Асинхронные данные** — `httpResource` / `rxResource` для загрузки
  с сервера.

Выбор обусловлен желанием использовать реактивность сигналов без
излишнего бойлерплейта, характерного для классического NgRx.

---

## 2. SignalStore (глобальное состояние)

Используется библиотека **@ngrx/signals**. Каждый стор — это фабрика,
создаваемая через `signalStore()`.

### 2.1. Текущие сторы

#### `AuthStore` (`core/store/auth.store.ts`)

**Состояние:**

| Поле | Тип | Описание |
|------|-----|----------|
| `user` | `{ email, fullName, roles } \| null` | Текущий пользователь. |
| `token` | `string \| null` | JWT-токен. |
| `isLoading` | `boolean` | Идёт ли сейчас запрос. |
| `error` | `string \| null` | Общая ошибка (не полевая), для баннера. |
| `registerSuccess` | `boolean` | Флаг успешной регистрации. |

**Методы:**

| Метод | Возвращает | Назначение |
|-------|-----------|------------|
| `login(email, password)` | `Promise<WmsProblemDetails \| null>` | Вход. `null` — успех. |
| `register(email, password, fullName, role)` | `Promise<WmsProblemDetails \| null>` | Регистрация. `null` — успех. |
| `logout()` | `void` | Очистка состояния и `localStorage`. |
| `loadUserFromStorage()` | `void` | Восстановление сессии при старте. |
| `clearError()` | `void` | Сброс общей ошибки. |
| `clearRegisterSuccess()` | `void` | Сброс флага после показа SnackBar. |

**Почему `async/await`, а не `rxMethod`.** Signal Forms
`submission.action` — `async`-функция. Внутри неё естественно
использовать `await`, а не реактивные операторы. Observable API-клиента
превращается в Promise через `firstValueFrom` из `rxjs`. Если позже
понадобится сложная реактивность (debounce, switchMap, retry) — вернёмся
к `rxMethod` на уровне конкретного запроса.

**Почему метод возвращает `WmsProblemDetails | null`.** Signal Forms
позволяет форме «разложить» серверные ошибки по полям, если
`submission.action` вернёт их в виде массива `ValidationError`. Чтобы
это работало, стор должен **пробросить объект ошибки наружу** — одного
`error()` в сторе недостаточно. Компонент получает `problem` и решает:
раскладывать по полям или оставлять баннером. См. паттерн в
[error-handling.md](./error-handling.md) §6.

**Правило «полевые ошибки — не в `error()`».** Если у `problem` есть
поле `errors` (ошибки по конкретным полям DTO), стор **не заполняет**
общий `error`. Это устраняет двойное уведомление: пользователь видит
`<mat-error>` под полем, а баннер сверху не показывается.

Реализовано через локальную проверку `hasFieldErrors(problem)`:

```typescript
function hasFieldErrors(problem: WmsProblemDetails | null): boolean {
  return !!problem?.errors && Object.keys(problem.errors).length > 0;
}
```

#### `NotificationStore` (план)

**Состояние:** список уведомлений, количество непрочитанных.

**Методы:** загрузка через `httpResource`, отметка о прочтении,
удаление.

## 3. Локальное состояние (сигналы)

Каждый компонент может иметь собственные сигналы для:

- Состояния формы — через Signal Forms (`form()`, `[formField]`).
- Параметров фильтрации и пагинации.
- Флагов загрузки (если не покрывается `httpResource`).
- Вычисляемых значений через `computed`.

Пример: `isChief` в `Dashboard` — производный сигнал от
`authStore.user()`:

```typescript
protected readonly isChief = computed(
  () => this.authStore.user()?.roles?.includes('Chief') ?? false,
);
```

---

## 4. Асинхронные данные — Resource API

Для **чтения данных** с сервера используется `httpResource` (или
`rxResource`). Они автоматически управляют состояниями `value`,
`error`, `isLoading` и перезагружаются при изменении сигналов-зависимостей.

Для **мутаций** (POST, PUT, DELETE) используется API-клиент напрямую
через `firstValueFrom`, после чего вызывается `reload()` у ресурса или
обновляется сигнал-зависимость.

---

## 5. Почему не классический NgRx?

- Меньше шаблонного кода — не нужны действия, редукторы, эффекты.
- Отличная интеграция с Angular 22 и реактивным стеком (сигналы,
  `httpResource`, Signal Forms).
- `patchState` работает напрямую, без `dispatch`.
- Компоненты читают состояние через вызов сигналов, не через
  `select()` + `async` pipe.

## 6. Правила использования

### 6.1. Где хранить состояние

- **Глобальный стор** — для данных, используемых в разных частях
  приложения (пользователь, уведомления, справочники с кешем).
- **Локальные сигналы** — для всего, что нужно одному компоненту
  (фильтры, пагинация, состояние модалки).
- **Resource API** — для всех GET-запросов с пагинацией и
  фильтрацией. Для POST/PUT/DELETE — API-клиент напрямую.

### 6.2. Как работать с асинхронностью

- **Не использовать `subscribe`** — вместо этого читать сигналы в
  шаблонах или использовать `computed` для преобразований.
- **Не забывать `firstValueFrom`** — для превращения Observable
  в Promise в `async` методах.
- **Не оставлять висящие подписки** — сигналы и ресурсы
  автоматически управляют временем жизни.

### 6.3. Как обрабатывать ошибки в сторе

- **Возвращать `WmsProblemDetails | null`** из методов-мутаций
  (`login`, `register`, будущие `create`, `update`, `delete`),
  чтобы вызывающий компонент мог разложить полевые ошибки по форме.
- **Заполнять `error()` только для не-полевых ошибок** — иначе
  баннер продублирует `<mat-error>`. Проверка — через
  `hasFieldErrors(problem)`.
- **Логику авто-logout на 401 не дублировать в сторе** — она
  реализована в HTTP-интерсепторе.

Подробнее — [error-handling.md](./error-handling.md) §4–6.

### 6.4. Как обновлять данные после мутации

- Если данные читаются через `httpResource` — вызвать `.reload()`.
- Если данные в локальном сигнале — обновить сигнал вручную.
- Не перезапрашивать весь список, если достаточно локального патча.
  Но и не пытаться держать кеш вручную — на этом уровне
  предсказуемость важнее «оптимизации».

---

## 7. Заключение

Гибридная модель управления состоянием — сигналы + SignalStore +
Resource API — обеспечивает высокую производительность, простоту и
соответствие современным подходам Angular. Ключевые договорённости:

- Глобальное — в `SignalStore`, локальное — в сигналах.
- Асинхронные чтения — через `httpResource`.
- Мутации возвращают `WmsProblemDetails | null` для раскладки
  серверных ошибок по полям формы.
- Ошибки обрабатываются на трёх уровнях (интерсептор → стор → форма).
